`Scanner` vs `BufferedReader`

Scanner

- 입력받은 데이터를 다양한 타입으로 변환하여 반환하는 클래스
- `java.util.Scanner` 패키지 사용
- 원하는 타입으로 읽을 수 있음
    
    ```jsx
    String answer = sc.nextLine();
    int answer = sc.nextInt();
    double answer = sc.nextDouble(); 등..
    ```
    
- 데이터를 입력받을 경우 즉시 사용자에게 전송되며, 입력받을 때마다 전송되어야 하기 때문에 **많은 시간 소요됨**
- 버퍼의 사이즈가 1024byte(1KB)

BufferedReader

- 데이터를 **한 번에 읽어와** 버퍼에 보관한 후, **버퍼**에서 데이터를 읽어오는 방식으로 동작하는 클래스
    
    <aside>
    
    버퍼 Buffer
    
    - 데이터를 한 곳에서 다른 한 곳으로 전송하는 동안 일시적으로 해당 데이터를 보관하는 임시 메모리 영역
    - 입출력 속도 향상을 위해 사용함
    </aside>
    
- `java.io.BufferedReader` 패키지 사용
- 데이터를 파싱하지 않고, **String으로만** 가져옴
- Checked Exception으로 **반드시 예외 처리**를 명시해야 함
- 문자가 입력될 때마다 CPU가 하나하나 입출력을 하는 것보다 버퍼에 쌓아두고 가득차거나 개행 일어날 때마다 입출력 처리하기 때문에 **실행 속도가 더 빠름**
- 버퍼의 사이즈가 8192byte(8KB)

### Scanner를 선택한 이유

작성한 코드에서 입력값을 `int`로만 받았기 때문이다. BufferedReader을 사용한다면 `String` 형식으로만 읽고 저장하기 때문에 `int`로 형변환해야하기 때문에 편의성을 위해 사용하였다.

### 상속

자식 클래스가 부모 클래스의 필드와 메서드를 물려받아 재사용, 확장할 수 있도록 하는 객체지향 개념 `extends` 

- 부모 클래스와 자식 클래스는 항상 고정된 관계 X

Top은 Clothes의 자식 클래스이지만, Blouse의 부모 클래스가 되기도 함. 상대적인 개념.

상속을 사용했을 때 장점

- 코드를 재사용하고, 공통된 기능을 한 곳에 모아 유지보수를 쉽게 하여 유연한 확장을 하기 위해
- 여러 클래스가 비슷한 필드나 메서드를 반복해 정의한다면, 나중에 수정해야 할 때 복잡해짐

### 인터페이스

구현 세부사항없이 클래스가 구현해야 할 메서드의 집합만을 정의한 설계 명세서

- 클래스 간에 “이 기능을 반드시 제공해야 한다”는 명시적 요구사항의 집합

```java
package poly.car1;

public interface Car {
    void startEngine();
    void offEngine();
    void pressAccelerator();
}
```

`인터페이스` vs `추상 클래스`

인터페이스

- 공통된 메서드의 이름만 정의하고, 그 구현은 강제 X
- “이 메서드를 반드시 구현해야 한다”는 ‘계약’을 정의, 구현 클래스는 인터페이스를 따르는 한 반드시 메서드를 재정의해야 함
- 구현을 강제, 유연한 구조 설계에 유리하므로 전략 패턴이나 의존성 주입 구조에서 널리 사용됨
    
    <aside>
    
    전략 패턴
    
    동일 계열 알고리즘군을 정의하고 캡슐화 → 각각의 알고리즘군을 수정해 쓸 수 있게 하는 패턴
    
    - 알고리즘의 여러 버전이 필요하거나 변형이 필요할 때
    - 알고리즘의 동작이 런타임에 실시간으로 교체되어야 하는 경우
    - 알고리즘 코드가 노출되면 안 되는 데이터에 접근하거나 활용할 때
    
    의존성 주입 구조
    
    - 스프링 프레임워크에서 중요한 개념
    - 스프링 컨테이너에서 객체 bean 먼저 생성해두고, 생성한 객체를 지정한 객체에 주입
    </aside>
    

추상 클래스

- 공통된 메서드의 정의 + 일부 구현도 함께 제공할 수 있음
- 일부 기능은 미리 구현해두고, 나머지는 자식 클래스에서 선택적으로 재정의 → 재사용과 확장 유도
- 공통 동작을 일부 구현해두고, **세부 동작만 자식에게 위임하고 싶을 때**

### wearable 인터페이스를 사용한 이유

‘옷’이라는 객체가 공통적으로 `wear()`의 기능을 가져야 한다고 생각했기 때문이다. 인터페이스를 사용하여 **“착용 가능한”이라는 규칙**을 만들었다. 근데 사용하고나서 느낀 점은 다른 기능도 더 포함하고 있었다면 좋았을 것 같다. 그리고 위의 `Car` 예시처럼 기계가 동작하는 기능들을 썼으면 인터페이스의 의미가 더 명확했을 것 같다. 

```java
@Override
    public void wear() {
        System.out.println(name + "를 입습니다.");
    }
```

### `super()`

부모 클래스의 생성자를 자식 클래스에서 호출할 때 사용

- 자식 클래스가 객체로 생성될 때 부모 클래스의 생성자가 먼저 실행되어야 하므로 컴파일러는 **자식 생성자 내부에서** `super()`를 가장 먼저 호출하도록 요구
- 자식 클래스에서 `super()`를 명시하지 않으면 부모클래스의 기본 생성자를 자동으로 호출.
- 부모 클래스에 기본 생성자 없고 매개변수가 있는 생성자만 있다면, 자식 클래스에서 반드시 `super(값)`형태로 적절한 부모 생성자 호출해야 함

```java
package ootd;

import ootd.acc.Acc;

public class Cap extends Acc {
  public Cap() {
        **super("모자");**
  }
}
```

### is - a 관계

A는 B이다. 상속 관계를 표현. 자식 객체를 부모 타입에 담을 수 있음

코드에서는 이렇게 쓰였다.

- `Top` **is a** `Clothes` 상의는 옷이다.
- `Cap` **is an** `Acc` 모자는 액세서리이다.

### switch()문을 사용한 이유

처음에 if-else문으로 작성하였다. 작성하고 보니 코드가 조금 지저분해보이는 느낌이 들었다. if-else문은 비교연산을 할 때 많이 사용했는데 `if (n < 5) { } else { }와 같은..` 물론 `if (n == 1)` 과 같이 사용할 수 있지만, 이보다는 switch문을 활용하여 **특정 값**일 때의 조건을 직관적으로 확인하기 위해 사용하는 게 낫다고 생각하였다. 

```java
int topChoice = sc.nextInt();
switch(topChoice) {
    case 1: top = new Blouse();
        break;
    case 2: top = new Tshirt();
        break;
    case 3: top = new Knit();
        break;
    default : System.out.println("잘못 선택하셨습니다.");
        break;

}
```
